# Archive Library — Storage, Schema, and Files

## Goals

The storage layer must support four categories without letting one overwrite
another:

1. **provider facts** observed from Twitter or a future source;
2. **archive facts** about requests, attempts, bytes, hashes, and aliases;
3. **owner curation** such as ratings, tags, notes, collections, and persona
   links;
4. **derived projections** such as FTS rows and previews.

Provider ingest owns only (1). Workers own (2). The UI/API owns (3). Any
component may rebuild (4). Re-ingesting an old record must never erase or
reset curation.

## Why the current schema needs a controlled generalization

The existing schema is a good capture/downloader substrate, but it encodes
assumptions that become unsafe in the library:

- `post_key`, tweet IDs, account IDs, and media keys are not service-namespaced;
- the latest capture of a tweet replaces `versions.raw_record_json`, so it
  cannot by itself reconstruct username/profile transitions over time;
- post `state` combines capture and archive workflow rather than recording
  archive requests and attempts independently;
- `files` combines the physical blob and its media relationship, while
  `UNIQUE(sha256)` allows only the first media item to own a deduped blob;
- a dedupe hit returns the first path but does not record a relationship from
  the second media asset to those bytes;
- sidecars are written but not catalogued or verified;
- a current `author_screen_name` is useful for display but insufficient for
  historical handles and cross-account personas;
- an in-memory queue cannot express leases, attempts, partial asset outcomes,
  or multiple durable job types.

Do not patch each issue with nullable columns on the Twitter tables. Add a
generic canonical model in the same SQLite database, backfill it, and cut the
runtime over as described below.

## Identifier rules

- Internal domain IDs are opaque UUID strings generated by the server. They
  are stable API identifiers and never derived from a mutable handle/path.
- Provider identifiers are always paired with `service_id`.
- A logical content item has a provider-native logical key. For Twitter this
  is `edit_initial_id_str ?? id_str`.
- Each provider version retains its own native ID. For Twitter, an edited
  tweet's IDs map to one logical item and multiple versions.
- A media asset uses the provider media key when present. A deterministic
  adapter key such as `tweet:<version-id>:position:<n>` is used only when the
  provider has no stable key.
- Hashes identify bytes, not posts or media semantics. Multiple media assets
  can and should link to one blob.

## Conceptual schema

This is a logical contract, not copy-paste DDL. The implementation plan must
turn each group into an ordered SQLite migration with foreign keys, checks,
and the indexes listed below.

### System and ingest

| Table | Important fields | Purpose |
|---|---|---|
| `schema_migrations` | `version`, `name`, `applied_at`, `checksum` | ordered, immutable migration ledger |
| `services` | `id`, unique `key`, `display_name`, `adapter_version` | `twitter` now; future provider namespace |
| `capture_devices` | `id`, `label`, `token_hash`, `created_at`, `last_seen_at`, `revoked_at` | independently revocable extension installations |
| `ingest_receipts` | `event_id`, `device_id`, `sequence`, `payload_hash`, `received_at`, `processed_at`, `status`, `error_code` | idempotency and acknowledgement boundary |
| `source_snapshots` | `id`, `service_id`, `entity_kind`, `native_key`, `first_observed_at`, `last_confirmed_at`, `fingerprint`, `payload_json`, `source_op`, `device_id` | retain meaningful provider changes without duplicating identical scroll captures |

`ingest_receipts` may discard successfully processed payload bodies after a
configured safety window, but retains the event ID/hash/sequence receipt.
`source_snapshots` retains normalized data when the meaningful fingerprint
changes. Volatile counts can be excluded from that fingerprint and handled as
current projections or sampled engagement observations; do not create a full
JSON copy every time the same tweet enters the viewport.

### Accounts and people

| Table | Important fields | Purpose |
|---|---|---|
| `accounts` | `id`, `service_id`, `native_id`, current handle/name/state, first/last seen | one provider identity; unique `(service_id,native_id)` |
| `account_profile_periods` | `id`, `account_id`, handle/name/bio/avatar/state, `first_observed_at`, `last_confirmed_at`, `fingerprint`, evidence snapshot | contiguous observed profile periods; append when fields change |
| `people` | `id`, `display_label`, `is_owner`, `notes`, timestamps | curated real-world/persona grouping |
| `person_accounts` | `person_id`, `account_id`, `linked_at`, `unlinked_at`, `reason` | manual aliasing across accounts/services with history |
| `viewer_accounts` | `account_id`, `label`, `active`, `added_at` | accounts belonging to the owner and usable as relationship viewpoints |

Only one active `people.is_owner=1` row is allowed. A service account may
have at most one active person link, but old links are retained with
`unlinked_at` for repair/audit. A repeated identical profile observation
updates `last_confirmed_at`; a changed handle/name/state closes the current
period and creates another.

### Content, versions, and relationships

| Table | Important fields | Purpose |
|---|---|---|
| `content_items` | `id`, `service_id`, `native_key`, `kind`, `author_account_id`, `created_at_ms`, `current_version_id`, `availability`, first/last seen, archive projection | one logical post; unique `(service_id,native_key)` |
| `content_versions` | `id`, `item_id`, `native_id`, text/lang/entities/counts/sensitivity, `created_at_ms`, first/last seen, raw snapshot reference | provider edits/versions; unique `(item_id,native_id)` |
| `content_native_ids` | `service_id`, `native_id`, `item_id`, `version_id`, `role` | fast resolution from any observed provider ID; unique `(service_id,native_id)` |
| `content_relationships` | `source_item_id`, `type`, nullable `target_item_id`, target service/native ID | reply, quote, repost, thread/parent links even before target capture |
| `content_observations` | `item_id`, `version_id`, `snapshot_id`, `source_op`, `captured_at`, `device_id` | provenance linking meaningful snapshots to canonical items |

`availability` is an evidence-based current projection such as `available`,
`deleted`, `withheld`, `account_unavailable`, or `unknown`. Store
`availability_observed_at` and an evidence snapshot/event. Never infer an
account deletion from one missing media URL.

The archive projection on `content_items` (`not_requested`, `queued`,
`partial`, `archived`, `failed`) is a query optimization maintained from
archive request/asset rows. It is not the job ledger.

### Media candidates and archived bytes

| Table | Important fields | Purpose |
|---|---|---|
| `media_assets` | `id`, `service_id`, `native_key`, `type`, dimensions/duration/alt text, first/last seen | semantic media identity; unique `(service_id,native_key)` |
| `content_media` | `version_id`, `asset_id`, `position`, `role` | ordered media membership per content version |
| `remote_media_candidates` | `id`, `asset_id`, URL, MIME, bitrate/size, priority, adapter metadata, first/last seen | provider URLs captured or derived by a provider adapter |
| `blobs` | `id`, unique `sha256`, `bytes`, `mime`, `storage_path`, `created_at`, `verified_at`, `missing_at` | one immutable physical byte object |
| `media_blobs` | `asset_id`, `blob_id`, `role`, `acquired_at`, `source_candidate_id`, `is_preferred` | many-to-many semantic relationship; fixes current dedupe ownership gap |
| `file_aliases` | `id`, `blob_id`, `item_id`, optional `asset_id`, `kind`, `relative_path`, `materialization`, timestamps | human/legacy paths, hardlinks, or recorded names |
| `sidecar_exports` | `id`, `item_id`, `version_id`, format/version, path, hash, generated_at | catalogue and verify generated `.txt`/`.json` artifacts |

`storage_path` is relative to a configured storage root; absolute paths do not
leave the server. The database may reference existing legacy files in place
after migration. A later compaction can move them into a content-addressed
layout, but the API cannot depend on that physical choice.

### Archive requests and durable jobs

| Table | Important fields | Purpose |
|---|---|---|
| `archive_requests` | `id`, `item_id`, requester/reason, requested/completed time, state, policy JSON | one user/rule/import request to acquire an item |
| `archive_request_assets` | `request_id`, `asset_id`, state, selected candidate, blob ID, error | per-media outcome and partial success |
| `jobs` | `id`, `type`, `dedupe_key`, `state`, priority, `run_after`, lease owner/expiry, attempt limits, payload JSON, last error, timestamps | generic durable work queue |
| `job_attempts` | `id`, `job_id`, attempt number, start/end, outcome, normalized error, metrics JSON | auditable attempts without logging secrets |

Job types initially include `archive_item`, `download_asset`,
`generate_preview`, `verify_blob`, and `import_scan`. A partial unique index
on `(type,dedupe_key)` for pending/running jobs prevents duplicate live work.
An archive retry creates or reactivates explicit work; failed downloads do
not silently retry forever.

### Source relationships and owner curation

| Table | Important fields | Purpose |
|---|---|---|
| `viewer_item_state` | `viewer_account_id`, `item_id`, nullable liked/bookmarked/reposted, observed time/evidence | current provider relationship from a specific owner account |
| `viewer_item_state_history` | same relationship fields plus period/observation | append only when an observed value changes |
| `item_curation` | `item_id`, nullable rating 1–5, local favorite, note, updated_at | post-level owner metadata |
| `media_curation` | `asset_id`, nullable rating 1–5, local favorite, note, updated_at | individual-media owner metadata |
| `tags` | `id`, unique normalized name, display name, color, description | owner vocabulary |
| `item_tags` / `media_tags` | target ID, tag ID, added_at | foreign-key-safe tagging at both supported levels |
| `collections` | `id`, name, description, sort mode, timestamps | explicit saved groups |
| `collection_entries` | collection ID, item/media target, position, note, added_at | ordered or query-sorted membership |

Provider relationships use nullable booleans: `NULL` means not observed,
not false. App-local favorite/rating never mirrors or mutates a provider.
Detailed semantics are in `06-identity-and-curation.md`.

### Import provenance

| Table | Important fields | Purpose |
|---|---|---|
| `import_sources` | `id`, label, source root fingerprint, adapter key/config, created_at | configured old archive source without exposing it to clients |
| `import_batches` | `id`, source ID, scan/commit state, manifest hash/path, counts, timestamps | reviewable unit of import work |
| `import_entries` | batch ID, stable source-relative key, path, size/mtime/hash, classification, parsed fields, proposed action, final object IDs, error | idempotency, reconciliation, and audit |

The initial importer is read-only with respect to source roots. See
`07-legacy-import.md`.

### Search and derived projections

- `content_fts`: current text, media alt text, current author handle/name,
  owner notes, and optionally tag display names. Keep provider text and owner
  notes in separate FTS columns so fielded search remains possible.
- Denormalized filter columns/indexes for service, created time, author,
  availability, archive state, rating, and media type.
- Precomputed item cover-media selection if the grid query needs it.
- Rebuild commands must be available for FTS and derived projections.

## Required indexes and constraints

At minimum:

- all provider lookup pairs `(service_id,native_id/native_key)` unique;
- content listing indexes beginning with common equality filters and ending in
  `(created_at_ms DESC,id DESC)` for cursor pagination;
- `content_items(author_account_id,created_at_ms DESC,id DESC)`;
- `content_media(version_id,position)` and `content_media(asset_id)`;
- `viewer_item_state(viewer_account_id,bookmarked,item_id)` and equivalent
  liked filtering;
- `item_tags(tag_id,item_id)`, `media_tags(tag_id,asset_id)`;
- `jobs(state,run_after,priority,created_at)` and lease expiry;
- unique blob hash and unique alias relative path;
- rating checks (`NULL` or integer 1–5), boolean checks, known-state checks;
- foreign keys enabled on every connection.

Use keyset/cursor pagination. Do not use deep `OFFSET` scans in media grids.

## File storage contract

### Originals

The logical store is content-addressed even if historical bytes remain in
legacy paths. For newly managed files, the preferred physical layout is:

```text
<original_root>/sha256/ab/cd/<full-sha256>
```

The write sequence is:

1. validate the provider candidate and redirect policy;
2. stream into a temporary file on the destination filesystem while hashing
   and enforcing size/time limits;
3. flush and close; inspect MIME by signature where practical;
4. in a transaction, reuse an existing hash or reserve a new blob row;
5. atomically rename the temp file into the final path if this hash is new;
6. link the asset/request to the blob regardless of dedupe;
7. materialize or record compatibility aliases and generate sidecars;
8. mark per-asset/request/job outcomes.

Crashes before promotion leave only age-cleanable temp files. Crashes after
promotion but before the transaction commit are found by an orphan scan. Never
write an original directly to its final name.

### Compatibility names and sidecars

Twitter's frozen basename remains available. Separate naming from physical
blob identity:

- Existing legacy files can be registered as the blob's physical path.
- New files may expose the frozen path as a hardlink/reflink when the
  filesystem supports it.
- If link materialization is undesirable, record the alias and offer it only
  through export/download naming; do not duplicate bytes merely to satisfy a
  directory view.
- A deduped media asset still receives its own `media_blobs` relationship and
  logical alias. Purging one post cannot delete a blob referenced elsewhere.
- Sidecars are versioned exports generated from the canonical DB and tracked
  with hashes. Preserve the current text/JSON format for Twitter compatibility;
  a future generic sidecar format uses a new filename or explicit version.

### Preview cache

Previews are derived from originals and stored outside the required backup
set, for example:

```text
<preview_root>/v1/<profile>/<blob-sha256>.webp
```

Initial profiles:

- `grid-320`: fit within 320 px, quality tuned for dense grids;
- `grid-640`: retina/larger cards;
- `detail-1280`: detail view without loading the original;
- `poster-640`: a still frame for video/GIF when available.

Preview identity includes generator version, source blob hash, dimensions,
format, crop/fit policy, and orientation handling. Write previews atomically.
Missing previews enqueue one deduped job; API callers receive a poster/original
fallback or a retryable placeholder. A rebuild may delete the entire cache.

Use `sharp` for images. Video still extraction through `ffmpeg` is a separate
capability check; the MVP can use captured poster images until it is installed.

## Migration from the current schema

### Preparation

1. Add a migration runner that starts from a declared legacy baseline.
2. Refuse startup on an unknown/newer schema version.
3. Create an online SQLite backup plus a file inventory before migration.
4. Run `PRAGMA foreign_key_check`, `integrity_check`, and current file verify.
5. Record pre-migration counts and hashes in a machine-readable report.

### Additive backfill

1. Insert the `twitter` service.
2. Convert distinct current author IDs into namespaced accounts; preserve
   nullable/missing IDs with deterministic unresolved-account records that can
   later reconcile.
3. Backfill `posts` into logical content items and current account profile
   periods.
4. Backfill `versions`, native ID lookup rows, relationships, source operation,
   and raw snapshots.
5. Backfill `media` into media assets, content membership, and candidates.
6. Backfill every `files` row into a blob plus media-blob relationship after
   confirming its current path/hash. Mark missing/mismatched rows, never guess.
7. Discover current sidecars adjacent to known media and catalogue them without
   rewriting.
8. Translate post archive state into an initial archive request/outcome.
9. Build FTS and filter projections from canonical rows.

### Verification and cutover

Required equivalence checks:

- every legacy post/version/media ID resolves to exactly one generic object;
- author/service mappings have no unexplained collisions;
- every valid legacy file hash is represented by one blob and at least one
  media relationship;
- archived/failed/deleted counts reconcile, with an explicit exception report;
- current FTS fixture queries return the same or broader correct results;
- re-ingesting all expected Twitter fixtures is idempotent;
- curation written before a repeated ingest remains unchanged;
- download dedupe across two media assets produces one blob and two links;
- purge of one of those assets retains the shared bytes until the last
  reference is removed.

After cutover, all runtime reads/writes use generic repositories. Keep the
legacy tables read-only for one release and backup cycle, then remove them only
through a separately reviewed migration. Do not keep indefinite dual writes.

## Retention and deletion semantics

- Captured metadata and originals default to infinite retention.
- Preview eviction is always safe.
- Successful ingest receipts can be compacted after the device acknowledgement
  and backup window; error receipts remain until resolved.
- Source snapshots may be compacted only by an explicit policy that preserves
  first/last observation and every semantic transition.
- Purge is dry-run by default and reports shared blobs, aliases, sidecars,
  curation, and import provenance.
- Deleting a content item removes a blob only if no media, import, export, or
  hold reference remains. Use a reference query, not a cached count alone.
- Provide a metadata-only purge separately from deleting archived bytes.
- No automatic garbage collector runs until its dry-run report and restore
  tests have been owner-approved.
