# Plan 02 — Network Layer: Passive GraphQL Capture, Request Parity

Goal: replace the dead REST data layer with one that (a) issues **zero additional API requests** in the common case, and (b) when a request is unavoidable, is **byte-identical in shape to what the browser itself sends**. This plan defines the interceptor, the tweet cache, the normalizer, and the (narrow) active-fetch fallback.

## 1. Why passive capture, not "fixed-up" active requests

The modern X web client calls `https://x.com/i/api/graphql/<queryId>/<OperationName>`. Replaying these ourselves has three problems:

1. **`x-client-transaction-id`**: since ~2023 X signs every API request with a per-request transaction ID generated by obfuscated client code (keyed from data served in the page HTML). It changes with client deploys. Requests without a plausible value are increasingly rate-limited/flagged. Re-implementing the generator is a permanent arms race (community re-implementations exist and break regularly).
2. **`queryId` rotation**: the GraphQL persisted-query IDs and the giant `features` parameter blob change with every web-client deploy. Hardcoding them (the old code hardcoded bearer tokens the same way, `timeline.js:468-469`) is the exact maintenance trap we're escaping.
3. **Account risk**: forged calls run against the logged-in session; anomalous patterns risk the *user's account*, not just the extension.

Meanwhile, **everything rendered on screen arrived via a GraphQL response we can observe**. The page already paid for the data; we just keep a copy. Zero extra requests, zero forged headers, zero queryId knowledge needed, and it inherently satisfies "identical to normal browser requests" — they *are* the browser's requests.

## 2. Interceptor (`content/page-interceptor.js`, MAIN world)

- Registered in the manifest as a content script with `"world": "MAIN"`, `"run_at": "document_start"` (Chrome 111+; Firefox 128+ supports `world` too — for older Firefox, inject a `<script>` tag from the isolated script as fallback).
- Patches, before the app boots:
  - `window.fetch`: wrap; if response URL matches the filter, `response.clone().text()` in the background and forward. Never delay or mutate the original response.
  - `XMLHttpRequest.prototype.open/send`: listen for `load`, read `responseText` when URL matches. (The X client has switched between fetch and XHR over time; patch both.)
- URL filter: `/\/i\/api\/graphql\/[^/]+\/(\w+)/` — capture the operation name. Start with a **pass-list** of operations known to contain tweets: `TweetDetail`, `TweetResultByRestId`, `TweetResultsByRestIds`, `UserTweets`, `UserTweetsAndReplies`, `UserMedia`, `Likes`, `Bookmarks`, `SearchTimeline`, `HomeTimeline`, `HomeLatestTimeline`, `ListLatestTweetsTimeline`, `CommunityTweetsTimeline`. Unknown operations: forward name-only telemetry in debug mode so the pass-list is easy to extend when X renames things.
- Forwarding to the isolated world: `document.dispatchEvent(new CustomEvent('twmd:graphql', { detail: JSON-string }))`. CustomEvent with string detail crosses the world boundary in both Chrome and Firefox (structured-clone quirks with objects in Firefox — use strings).
- **Hard rules:** the interceptor must be dependency-free, small (<150 lines), must never throw into the page (wrap everything), and must never modify request or response. It is the most fragile placement in the system; keep it boring.

## 3. Normalizer (`content/graphql-normalize.js`, isolated world, pure functions)

Turns a raw captured payload into `TweetRecord[]` (contract in 00-overview). Must handle the known envelope shapes:

- Timeline instructions: `data.*.instructions[]` → `TimelineAddEntries` / `TimelinePinEntry` / module items; entries → `content.itemContent.tweet_results.result`.
- `TweetDetail` threaded conversation entries (includes replies — each is a full tweet; cache them all).
- Result wrappers: `Tweet` vs `TweetWithVisibilityResults` (unwrap `.tweet`), `TweetTombstone` / `TweetUnavailable` — don't cache, but **emit a tombstone event carrying the entry's tweet id** when it can be derived (entryId); plan 06 uses these to flag deleted posts passively (Decision 18).
- Nested tweets: `legacy.retweeted_status_result`, `quoted_status_result` — recurse; cache the inner tweets under their own IDs and record the relationship on the outer record.
- Text: prefer `note_tweet.note_tweet_results.result.text` (long-form posts) over `legacy.full_text`; expand `entities.urls[].expanded_url` into the text; strip the trailing `https://t.co/…` media link.
- Media: `legacy.extended_entities.media[]` → type, `media_url_https`, `ext_alt_text`, `video_info.variants` (keep all; selection happens at save time), `original_info` w/h, `media_key`.
- Counts: `legacy.{reply_count,retweet_count,favorite_count,quote_count,bookmark_count}` + `views.count`.
- User: `core.user_results.result` — note X moved `screen_name`/`name` between `legacy` and `core` in 2024/25 builds; read both locations.

**Testing is the point of this module:** capture 6–10 real payloads (one per operation type, personal data redacted) into `test/fixtures/graphql/`, assert full `TweetRecord` output. When X changes shape, the fix is: drop in a new fixture, fix this one file until tests pass.

## 4. Tweet cache (`content/tweet-cache.js`, isolated world)

- In-memory `Map<id_str, TweetRecord>`, LRU-capped (~5,000 records; a record is ~2 KB → ~10 MB worst case). Newer capture wins (later payloads have fresher counts).
- Per-tab and per-navigation lifetime is fine — the page always re-fetches what it renders, so anything visible is (re)captured. **No persistence in v1** (IndexedDB adds failure modes; add later only if a real gap shows up).
- Known gap: extension installed/reloaded *after* the page loaded → cache is empty for already-rendered tweets. Handle by prompting the page to refetch (see §5 fallback ladder) rather than persisting.
- Emits `onUpdate` events; the UI layer (plan 03) uses them to enable buttons, the bulk downloader (§6) uses them as its data feed.

## 5. When data is needed but not cached — the fallback ladder

For a per-tweet download where the clicked tweet isn't in the cache (should be rare):

1. **DOM extraction** — for photos, the rendered `<img src="https://pbs.twimg.com/media/…?name=…">` gives the media ID; rewrite to `name=orig`. Text/author/date are also in the DOM. Covers photos fully without any request. (This is roughly what the legacy code did as its own fallback, `main_react.user.js:4340-4358`.)
2. **Provoke the page** — for missing video variants: the data arrives via the page's own `TweetDetail` when the status page/media viewer opens. UI hint: "open the tweet to enable video download". Zero forged requests.

**REJECTED (Decision 2, 00-overview): there is no rung 3.** An earlier draft allowed an opt-in
active `TweetResultByRestId` fetch as a last resort; the owner rejected it — the extension never
issues API requests itself, full stop. The ladder ends at rung 2. (Do not re-propose this;
the header-template capture described in plan 06 §1 exists for the app's *CDN* fetches only.)

Media byte fetches (images/videos) are *not* API calls and are always allowed: plain `GET` to `pbs.twimg.com` / `video.twimg.com` with no custom headers — identical to the user clicking "open image in new tab". Images: `?format=<ext>&name=orig` (fallback `name=4096x4096` then `large` on 404). Videos: highest-bitrate `video/mp4` variant from the cached `video_variants` (these are direct CDN mp4 URLs; no HLS handling needed when the variant list is available).

## 6. Bulk download without forged pagination

The legacy bulk feature paginated dead REST endpoints itself. Replacement: **the scroll driver**.

- User opens the timeline they want (profile Media tab, Likes, Bookmarks, search results) and starts bulk download from the dialog.
- The driver programmatically scrolls (`scrollBy` + wait; respect a floor of ~1.5–2.5 s jittered between steps) — the page issues its own paginated GraphQL requests; the interceptor/cache ingests them; the downloader consumes `onUpdate` events, applies the existing filters (tweet-ID range, count limit, media types, include-RTs), fetches media, and feeds the ZIP.
- Stop conditions: reached limit / passed the ID range / no new entries after N scrolls (end of timeline) / user pressed stop. Then finalize ZIP exactly as today (log + CSV inside, same names).
- Honest trade-off to document in the UI: slower than raw API pagination, but rate-limited *by the page itself*, undetectable, and immune to queryId churn. It also inherits X's own limits (e.g. Media tab depth) — same limits the user has in the browser anyway.

## Acceptance criteria

- Browsing home/profile/media/likes/bookmarks/search/status pages populates the cache (visible in a debug overlay/console command) with correct `TweetRecord`s — verified against fixtures in CI and against the live site manually.
- No request with a forged `authorization` or `x-client-transaction-id` header is ever emitted in default configuration (verify with DevTools network export during a full feature walkthrough: the only extension-originated requests are media `GET`s).
- Interceptor survives page navigation (SPA route changes) and does not break the site when X deploys an unknown operation (fails open, logs in debug mode).
